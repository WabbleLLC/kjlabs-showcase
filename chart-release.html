How a release ships

The engineering discipline behind every update: the engineer's own markup is the test, and every public number needs a source.

Step by step

  1. Start from the engineer's markup or a field request, not a paraphrase of it.
  2. Change the tool, then run automated tests that check real geometry and the duct node graph, not just on-screen text.
  3. Run truth checks: every number on a public page must trace to a registered source.
  4. Walk it live the way the engineer actually clicks: build both sides of a run, branch mid-run, delete things.
  5. Compare with the original markup. Release with a changelog only when it matches.

Why it is built this way

This process came out of a real failure. A run of releases passed every automated test, but they didn't do what the engineer expected, and an audit against his own markups found the underlying bug. Since then a passing test count doesn't count as proof that a release works.
